# What we hope to learn through pilots

We hope to gain insights on the topics below through pilots. We welcome pull requests on this document to add considerations.

## Licensing topics

* We anticipate that different projects will have different licensing needs or preferences. We expect to have some diversity of licensing. For CanIVC we plan to use Apache 2.0 and will learn from this choice. In the longer term we are likely to document some principles to help guide licensing decisions.
* For the CanIVC project we are experimenting with gathering contributor agreements (CLA) for the purpose of making it easier for W3C to relicense the aggregate of contributions (if that proves necessary). We recognize that collecting CLAs creates friction for some contributors (e.g., because they may need to do more to consult with legal departments) and there is a small cost to managing those CLAs for W3C. Through the pilot we hope to gain a better understanding of tradeoffs. 
   * Another question: our expectation is that it will be public knowledge who signed the CLA for a given project. We welcome feedback on that choice.
   
## Governance topics

### Program governance

* How does governance of an open source program relate to other areas of governance at W3C, and in particular the Membership?
* Are there any implications on representation in the Board of Directors based on a new set of stakeholders independent of Membership?
* Which [W3C operational principles](https://www.w3.org/TR/w3c-vision/#op-principles) apply directly to an open source program and which do not?
* How do we choose which projects to bring into the program (and which we do not)?
* How are choices made to change the status of the project (e.g., to “advance it” in the program to a more mature state in its lifecycle, or to archive it)?

### Project governance

Open source projects should be as self-governing as possible.

* What should be a minimal set of requirements for project governance (e.g., adherence to the W3C code of conduct and antitrust and competition policy, rules regarding the use of the W3C brand)?
* Will there be a requirement for transparency of decision making (e.g., everything is public by default, with the exception for security vulnerabilities)?
* Should there be an appeal path for technical disputes within a project? For process disputes? What would such a path look like?
* What would we expect to be “chartered” for every project (if any)? Examples:
  * Who gets to decide who gets what privileges on the main code base or supporting infrastructure (if any)? How do these privileges get updated?
  * How does the project prioritize features/bug fixes?
  * What is the policy regarding AI-generated contributions?
  * What versioning/release mechanisms are projects expected to use?
* What type of governance will be appropriate for projects that involve or are used by different stakeholders in the ecosystem (e.g., tools used by multiple organizations)?

## Project lifecycle

* At this early stage in the development of an open source program we do not have a crisply-defined definition of project lifecycle. For comparision, see the [Linux Foundation open source project lifecycle](https://www.linuxfoundation.org/blog/blog/the-lifecycles-of-open-source-projects) and the [Apache Project Maturity MOdel](https://community.apache.org/apache-way/apache-project-maturity-model.html). We anticipate developing a lifecycle for projects at W3C but need more experience, and the relationship to a future governance model.

## Support considerations

* How will W3C handle vulnerability reports? W3C has mechanisms in place for reports related to its own IT systems, and to chartered groups and their specifications. Do those suffice or will more be needed?

## Regulatory considerations

* Does W3C need to fulfill the requirements of a Steward under the Cyber Resilience Act?
